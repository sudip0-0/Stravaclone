## Encrypted local-storage and backup model

- Recording SQLite is configured for SQLCipher. A random 256-bit key is stored in SecureStore with `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, allowing locked-screen access only after the device has been unlocked once since boot and preventing key migration to another device.
- Android backup is disabled. iOS uses `NSFileProtectionCompleteUntilFirstUserAuthentication`, disables file sharing/open-in-place, and relies on the non-migratory SecureStore key: an encrypted database copied without its key is unusable. OS/vendor backup behavior and uninstall semantics still require device validation.
- Existing plaintext development databases from the pre-SQLCipher implementation are not claimed to migrate in place; clear the development app data before installing this build. No released production migration exists. A future shipped plaintext-to-encrypted migration requires a separately reviewed export/rekey procedure.
- The SQLCipher key is database-wide because the database may retain drafts for multiple owners; deleting one account cannot destroy the shared key without destroying other owners’ data. Owner deletion enables SQLite `secure_delete`, removes owner rows transactionally, checkpoints WAL, and attempts `VACUUM`, but flash translation layers, OS snapshots, and backups prevent a claim of immediate cryptographic erasure. The shared key is retained until app-data removal/uninstall or a future explicit “delete all local data” operation.
- Recoverable non-pending drafts are retained for at least 24 hours and are considered abandoned after 30 days, when startup maintenance may purge them. Pending upload jobs, source points, and pause intervals are retained indefinitely until a confirmed Phase 4 server response or explicit owner/account deletion. After a confirmed response, one SQLite transaction deletes the full local session/source and cascading sync job; timeout or unknown-commit paths never purge source data.
- Account cleanup intent is a durable state machine: `prepared` exists before the request, `confirmed` is written only after a definite 2xx deletion response, and `unresolved` records timeout/network/5xx ambiguity. SQLite confirmation must update exactly one prepared row. If SQLite confirmation fails after 2xx, Trail writes an owner-UUID-only SecureStore fallback using `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`; startup processes DB-confirmed and secure fallback authorization, purges, then clears the fallback. Credentials are cleared only after DB confirmation, secure fallback, or successful immediate purge. If all three fail, the app enters blocking Cleanup required state and prevents account switching while retrying. `prepared` and `unresolved` never authorize deletion; they preserve same-owner data and require manual reconciliation. Unconfirmed intent markers expire after 90 days without deleting owner data. Settings → Resolve deletion attempt can cancel `prepared`/`unresolved` while keeping data; confirmed cleanup cannot be cancelled. Definitive non-timeout 4xx responses cancel `prepared` immediately.
- **BLOCKED gates:** verify key creation and reopen after process death; locked-screen reads after first unlock; failure before first unlock after reboot; Android backup exclusion; iOS encrypted backup/restore to same and different device; uninstall/reinstall; and no key/raw coordinates in logs.
